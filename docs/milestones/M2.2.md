# Milestone M2.2 — leakage-safe historical aggregates (FS2)

M2.2 implements FS2 as FS1 plus point-in-time user/video engagement aggregates. It does not implement FS3, sequence history, or model training.

## History and cutoff

The sole history source is the normal-policy log from Apr 9–29, 2022. For an impression on calendar day `d`, the as-of lookup permits only normal rows whose `date < d`. Normal-training rows can therefore use earlier normal-training days; randomized-training rows use the same normal-only history and never randomized outcomes. Every impression for the same entity and day receives the same cutoff.

Only normal-training and randomized-training feature tables are materialized. Validation and final-test tables and outcomes are untouched.

## Smoothing

FS2 freezes additive smoothing at `alpha = 20` without tuning. Priors were computed once from the Apr 9–11 normal burn-in and written to `configs/fs2.toml` before FS2 materialization:

| Task | Numerator / denominator | Prior |
|---|---:|---:|
| Long view | 188,227 / 559,379 | 0.3364927893 |
| Like | 10,115 / 559,379 | 0.0180825523 |
| Tab-1 valid play | 215,375 / 403,667 | 0.5335462151 |
| Tab-0 literal click | 8,469 / 86,519 | 0.0978860135 |

Each rate is `(positive_count + 20 × prior) / (eligible_impression_count + 20)`. An unseen entity gets zero raw counts and exactly the corresponding prior. Priors are recomputed from the authorized burn-in at build time and must match the frozen configuration exactly.

## Feature contract

For each of `user` and `video`, FS2 adds:

- prior total impression count;
- prior long-view positive count and smoothed rate;
- prior like positive count and smoothed rate;
- prior tab-1 valid-play eligible count, positive count, and smoothed rate;
- prior tab-0 literal-click eligible count, positive count, and smoothed rate.

This is 11 fields per scope and 22 fields total. Counts are `Int64`; rates are `Float64`. There is deliberately no pooled click count or rate. Click histories from other tabs are excluded from both approved click strata.

All FS1 columns, types, order, and `impression_id` values are carried forward. Labels remain separate and are byte-for-byte copies of the authorized FS1 label artifacts.

Following M2.4a, FS2 features are explicitly written in ascending `impression_id` order, and the copied canonical labels must match position by position. A versioned build manifest records the row and schema contract.

## Reproduction

```bash
source .venv/bin/activate
python scripts/build_fs2.py

```
