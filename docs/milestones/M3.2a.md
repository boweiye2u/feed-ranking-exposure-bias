# Milestone M3.2a — LightGBM training infrastructure

M3.2a implements the data, categorical-encoding, task-mask, deterministic training, prediction, and serialization interfaces required for the frozen LightGBM experiments. It does not run the experiment matrix or access validation/test outcomes.

## Feature contract

The M2 `m2-features-v1` manifest is the column and dtype authority. Alignment metadata (`impression_id`, `user_id`, `video_id`, `date`, and `time_ms`) and every outcome are excluded from the LightGBM matrix. `context__is_rand` is excluded from all normal-only models.

| Feature set | Model fields | Categorical | Numerical |
|---|---:|---:|---:|
| FS1 | 44 | 35 | 9 |
| FS2 | 66 | 35 | 31 |
| FS3 | 83 | 36 | 47 |

The categorical declarations in `configs/fs1.toml` are preserved even when released codes are stored numerically. Thus anonymous one-hot codes, range buckets, author/music identifiers, interface `tab`, and other documented category codes are not treated as continuous ordinal measurements. Booleans and genuinely continuous/count/rate features remain numerical.

## Encoding

Each feature set gets a vocabulary fitted on all authorized normal-training rows and on no validation, randomized-training, or test row. Typed category tokens are sorted deterministically:

- code 0: missing value;
- code 1: category absent from the fitted training vocabulary;
- codes 2 and above: known training categories.

String values are encoded whole. `video__tag` and FS3 `category__key` are each single categorical fields; multi-valued and canonical tag sets are not exploded, pooled, hashed, or converted into additional features. Numerical nulls remain `NaN` for LightGBM's native missing-value handling.

The adapters verify manifest version/hash, exact feature names, order, and dtypes. Saved model bundles bind the LightGBM model, adapter checksum, feature-manifest checksum, feature set, task, complexity, and infrastructure version. Reload rejects incompatible or modified bundles.

## Tasks and masks

| Task name | Released label | Normal-training mask | Rows |
|---|---|---|---:|
| `long_view` | `long_view` | all rows | 722,481 |
| `like` | `is_like` | all rows | 722,481 |
| `valid_play` | `is_click` | tab-1 / `valid_play` semantics only | 535,569 |
| `literal_click` | `is_click` | tab-0 / `literal_click` semantics only | 78,575 |

The remaining 108,337 rows have unsupported click semantics and enter neither click task. A pooled `is_click` task is explicitly rejected. ESMM remains excluded.

## Fixed configurations

Both configurations use binary objective, learning rate 0.05, 300 rounds, minimum 100 rows per leaf, L2 penalty 1.0, full row/feature fractions, max bin 255, one thread, forced column-wise deterministic execution, and seed 202211. They differ only in tree capacity:

| Configuration | `num_leaves` | `max_depth` |
|---|---:|---:|
| `shallow` | 31 | 6 |
| `deep` | 127 | 10 |

These values are fixed infrastructure defaults, not validation- or test-tuned results.

## Planned matrix

The six model configurations are FS1/FS2/FS3 × shallow/deep. Each configuration trains eligible separate binary models for long view, like, tab-1 valid play, and tab-0 literal click. This is up to 24 task-specific fits, but still six feature/complexity configurations in the frozen comparison population.

Comparisons across feature sets and depths are valid within the same task because the task mask is identical. Long-view and like metrics concern different outcomes and are not numerically interchangeable. Valid-play and literal-click results use different interface populations and must not be directly compared or pooled. Literal-click performance on T-random will not be claimed because the audited random test population lacks tab-0 support.

## Reproduction

```bash
source .venv/bin/activate
python scripts/audit_lightgbm_interface.py
pytest -q
```

The audit fits and saves adapters only; it trains no model. Outputs are under `~/recom/models/lightgbm/infrastructure/v1/`.
